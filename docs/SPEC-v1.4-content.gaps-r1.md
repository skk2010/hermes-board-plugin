1. MAJOR — new-actionable — Table size has three incompatible meanings. X3.3 promises auto-size **when dimensions are absent** (`docs/SPEC-v1.4-content.md:109-110`), but the fixture's two tables have explicit `w: 0, h: 0` (`docs/fixture-v1.4.json:22-26,43-47`), while `tests/test_editor.py:420-426` expects the first to render at 180×100. The existing rectangle/bounds consumers read raw dimensions (`vendor/boardkit.py:522-523,596-604,679-680`; `vendor/board_editor.js:361-370,532-548`). Merely auto-sizing in `tableSvg` can make the visible table differ from its edge anchors, selection/resize geometry, guides and canvas bounds; interpreting zero literally instead collapses the fixture. Fix: pin whether zero is an auto-size sentinel, centralize effective table geometry for *every* reader in both renderers and the editor, and explicitly specify how absent/zero dimensions are materialized or resolved by the ops/panel writers. Gate the fixture's rendered dimensions, edge anchors, hit/handle bounds and canvas coverage, not just divider coordinates.

2. MAJOR — new-actionable — The tool cannot create the specified textless table without an explicit exception. X3.2 says table `text` is not drawn (`docs/SPEC-v1.4-content.md:105-107`), and X8 says `add_node` accepts table fields and writes onto the library builder's dict (`:194-203`), but `store.py:511-525` requires nonempty `text` when `parts` is absent, before calling `box`, and supplies 190×72 by default. Reproduced on a scratch copy of `store.py`/`vendor/`: `apply_ops(new_board(), [{"op":"add_node","kind":"table","rows":3,"cols":2,"cells":["a","b"]}])` and the same op with `"text":""` both raise `ValueError: add_node: missing text`. This baseline is expected to change, but the frozen spec never assigns the necessary exception or tool auto-size behavior; following only its field-writing instruction retains both defects. Fix: require `add_node(kind="table")` to allow missing/empty `text`, establish table defaults before normalization, and use the table's effective size instead of the box builder's defaults when w/h are omitted. Exercise a headerless/textless table through `board_apply`, not only a hand-written fixture.

3. MAJOR — new-actionable — Header geometry reserves an unassigned band. X3.1 says `header: true` makes the **first row** the bold header (`docs/SPEC-v1.4-content.md:98-101`); X3.3 sizes a 3-row table to `28 + 24*3` and places its first horizontal divider at `header_h + cell_h = 52` (`:109-119`), an expectation repeated in `tests/test_editor.py:420-426`. If row zero is the first of the three cells, it occupies y=28..52, with y=0..28 blank and no divider at y=28; if the 28px band is itself the header, the six cells of the 3×2 table need a fourth row or a different mapping. Fix: pin whether the header is a distinct band or row zero, the starting y and height of each cell, and the divider at the header boundary; update the pinned test coordinates and assert that the header cells actually occupy the intended top band in both renderers.

4. MAJOR — new-actionable — Panel applicability omits existing selectable kinds. X1 enumerates eight ordinary node kinds, plus table, area and note (`docs/SPEC-v1.4-content.md:62-69`), but the existing picker also offers `caption`, `server`, `computer`, `actor` and `note` (`vendor/boardkit.py:41-43,1094-1096`). A `kind:"note"` can live in `nodes` (the v1.4 fixture does so at `docs/fixture-v1.4.json:132-141`), whereas a note in `notes` has selection type `note` (`vendor/board_editor.js:73-81,682-704`). Moreover, X1 offers parts/split/count on all eight ordinary node kinds, although both renderers use parts only for `box`/`pill` (`vendor/boardkit.py:949-952`, `vendor/board_editor.js:427-430`). A map keyed only by selection type, or one with no entry for the omitted kinds, exposes inapplicable controls or hides text/kind/size controls needed for captions/icons. Fix: specify a per-kind row map (parts/split/count only on box/pill), and distinguish node-kind `note` from a `notes`-collection note (or explicitly migrate/forbid one representation). Add panelhide cases for diamond, both note representations and an icon/caption.

5. MAJOR — new-actionable — Bold is specified as applying to icon captions, but its only emission rule cannot affect them. X4.1 includes icon captions in the node's own formatted text (`docs/SPEC-v1.4-content.md:135-138`); X4.3 only changes a text element that would otherwise be weight 600 to 700 (`:145-146`). Both current icon caption paths emit `font-weight="400"` (`vendor/boardkit.py:943-946`, `vendor/board_editor.js:355-358`), and the `caption` kind emits no weight at all (`vendor/boardkit.py:925-929`). A literal implementation makes `bold:true` a no-op for these kinds. Fix: state that bold applies to every eligible node-own text path, overriding its existing weight with 700 only when true while preserving absent/false bytes, and test icon/caption true, false and absent in both renderers.

6. MAJOR — new-actionable — The split count stepper deletes existing part subtitles. X2 says `+`/`−` mutate the textarea and then behave exactly like typing (`docs/SPEC-v1.4-content.md:82-94`). The current typing handler preserves `part.sub` only when the **new line count equals the old count**; otherwise it reconstructs every part as `{text}` (`vendor/board_editor.js:1102-1118`). Thus adding a fourth line to a three-part box erases all three existing subtitles, even when their texts have not changed; removing it cannot restore them. Part subtitles are real document/rendered data (`vendor/boardkit.py:485-499,897-909`). Fix: specify an index-preserving insertion/deletion update for the stepper (and any count-changing textarea edit), or another lossless representation; assert surviving parts retain their `sub` across `+`, `−` and undo on a fixture with subtitle-bearing parts.

7. MAJOR — new-actionable — The guide self-test demands movement that snap-off forbids. X6 says `snap:false` draws guides but **nothing is nudged** (`docs/SPEC-v1.4-content.md:172-174`); its mandatory `guides` step drags to within approximately 2px with snap OFF and requires the two left edges to be **equal after drop** (`:177-180`). A two-pixel near miss cannot become exact equality without a nudge, so a correct implementation fails the prescribed test or a passing implementation violates snap-off. Fix: with snap off assert the guide appears, the near-miss position remains unchanged and the guide clears; require exact edge equality only with snap on. Use a deliberately off-grid target to prove guide-over-grid precedence.

8. MAJOR — new-actionable — Arrange is promised for selections the current panel cannot present or arrange. X7 exposes buttons with 2+ selected items and aligns/spreads their boxes (`docs/SPEC-v1.4-content.md:182-192`), while X1 closes the panel for a group primary (`:69-71`) and the existing ordered selection can contain groups and edges (`vendor/board_editor.js:42-44,91-110,727-737`). A group-first group+node selection has no panel in which to show the buttons; two selected edges have no item boxes/positions to align, but meet the 2+ rule. Additionally, X7 says align uses the bounding box while *the extreme items stay put* (`:187`), which is impossible for align-left on a non-aligned leftmost/rightmost pair. Fix: define eligibility by the count of geometric node/note/group items, the handling of selected edges, and access to arrange when a group is primary; say which reference edge/centre each align operation uses and which, if any, item stays fixed. Test a group-primary mixed selection, an edge-containing selection, and align-left on unequal x positions.
