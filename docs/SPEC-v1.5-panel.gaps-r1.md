# SPEC v1.5 panel — independent gap pass, round 1

Confirmed against the checked-in base and a scratch-copy renderer probe (not the editors' gates): `rows` includes the header, and the fixture's `t2`, `t3`, `t1` resolve respectively to 180×76, 270×48, 180×48 (`vendor/boardkit.py:548-568`; `docs/fixture-v1.5.json:10-84`). For `t2`, the widths are 120/60, the divider is at 120, the interior row ends are 28/52, and the text baselines are 19/45/69 (`vendor/boardkit.py:993-1025`). The effective tone matrix under the specified precedence is `[default, accent; muted, muted; default, warn]`; four cells need overlays. All six named tones have `-fill` and `-line` variables, with a dark-mode line override (`vendor/boardkit.py:40,1135-1154`); for valid tones the stated fallback order is total, and the existing foreground text variable does not depend on a cell's tone. These are checks of the formula and existing variables, not claims that the in-flight v1.5 renderers work. No editor gate was run.

Standard: no `AGENTS.md` invariants block or `SECURITY.md` exists. I used the requested fallback: the frozen spec must suffice for a worker with this repo and no other context, and must be internally consistent; the checked-in v1.4 implementation, the v1.5 fixture and existing checks are independent reality checks. This is v1.5's first pass; earlier waves' reports are not prior findings for this artifact.

1. MAJOR — Y4.2/Y4.5 — new-actionable — Cell x coordinates contradict unequal widths. `docs/SPEC-v1.5-panel.md:109-112` gives `t2` columns 120 and 60 wide, but `:125-129` positions left/centre/right text with `cell_w * c` and a single `cell_w`. A second-column centre must be x=150 and its left inset x=126; an equal-width interpretation yields 135 and 96. The right edge x=174 happens to agree under both formulas, so `tests/test_editor.py:518-521` does not distinguish them. Fix: specify `x0[c] = sum(widths[:c])`, then left=`x0+6`, centre=`x0+widths[c]/2`, right=`x0+widths[c]-6`; test left and centre in the narrow second column on both renderers.

2. MAJOR — Y4.5/Y4.6/Y0 — new-actionable — The pinned font sizes disagree and byte identity cannot hold under the Y4.5 number. `docs/SPEC-v1.5-panel.md:125` says cell font 12, while `:141-147` says use the renderer's `FONT` (today 12.5) and keep v1.4-shaped tables byte-identical; both checked-in paths emit 12.5 (`vendor/boardkit.py:987-990,1024-1025`; `vendor/board_editor.js:393-395,420-422`). Fix: replace the literal 12 in Y4.5 with `FONT`/12.5, and assert the existing v1.4 text attributes stay unchanged.

3. MAJOR — Y4.6/Y7 — new-actionable — The fixed 24/28 row bands account for the auto height but not an explicitly taller table. `docs/SPEC-v1.5-panel.md:135-145` declares `h = 28 + 24*(rows-1)` and no empty band, while Y7 `:236-240` forbids changing existing geometry. An explicit positive `h` is respected today (`vendor/boardkit.py:563-568`; `store.py:832-836`; `tests/test_render.py:396-399`). With `rows=2, header=false, h=90`, two 24-high bands cover only 48 of the 90 units; the last 42 have no cell, although dividers span `h` (`vendor/boardkit.py:1000-1025`). Fix: explicitly scope the equation to auto height and specify how explicit-height bands fill `h` (or deliberately document the unused region); retain and gate the v1.4 explicit-size case in both renderers.

4. MAJOR — Y1.5/Y4.7 — new-actionable — “Visible exactly when changing the field changes SVG” is not a per-kind mechanical predicate without a state/field policy. The existing split path ignores `sub` whenever parts render (`vendor/boardkit.py:1077-1082,1098-1103`), and ignores `split` when no parts render (`:1077-1082`; see `vendor/board_editor.js:558-561`). Yet both rows currently belong to every box/pill bucket (`vendor/board_editor.js:1345-1351`). A `kind:"note"` in `nodes` does render `sub` and `align` (`vendor/boardkit.py:1083-1103`) and changing `kind` alters its shape, although its current bucket omits kind/sub/align/text size/bold (`vendor/board_editor.js:1345-1358`); a note in `notes` cannot have a kind but, after Y4.7, must expose text size/bold. The self-test prescribed at `docs/SPEC-v1.5-panel.md:160-167` cannot infer one stable answer from one sample per kind, and it also needs a declared exception for cell row/column pickers, which change selection but not SVG (`:177-180`). Fix: pin an applicability matrix distinguishing node-note and notes-note, identify state-dependent rows and non-rendering picker controls, then probe appropriate discriminating states per field instead of asserting one render-difference set per kind.

5. MAJOR — Y2/Y5 — new-actionable — Cell alignment has no specified way back to inheritance. `docs/SPEC-v1.5-panel.md:179-183` gives only `left|center|right` cell buttons yet requires clearing both align and tone to turn an object cell back into a string; Y2 `:82-84` requires exactly one pressed button per group. Tone has an explicit `data-tone=""` clear swatch (`:180`), but alignment has no inherit/empty button and a pressed value cannot be cleared while exactly one remains pressed. Choosing `center` is not equivalent to clearing it when the table's own align is `left` (`:125-129`). Fix: add an explicit inherit/no-own-align choice (and define its pressed semantics), or specify a toggle-to-none exception; test inheritance after clear when table align is non-centre.

6. MAJOR — Y5 — new-actionable — “Unchanged textarea” destroys object-cell formatting on an unrelated text edit. `docs/SPEC-v1.5-panel.md:174-183` retains one-line-per-cell editing alongside `{text,tone,align}` entries; the current sync joins the entire cell list and the input handler replaces it wholesale with strings (`vendor/board_editor.js:1405-1418,1686-1694`). Even if display is updated to show object `.text`, replacing another line with the unchanged handler discards the first cell's tone/align. The row/col handlers also rebuild `cells` through the old string-list helper (`:1666-1684`). Fix: specify index-preserving text updates and row/column remapping that retain each surviving cell's own tone/align; test that editing cell 2 does not erase cell 1's object fields, and that resize preserves surviving cells.

7. MAJOR — Y6/Y4.1/Y4.2/Y3 — new-actionable — The same invalid input is both normalized and rejected. `docs/SPEC-v1.5-panel.md:104-117` says unknown cell tone/align are ignored and invalid/nonpositive `col_widths` entries become 1, and `:193-200` says `add_table` uses that normalization while `update_node` raises `ValueError` for an unknown tone or non-tristate align. `:92-95` says the pane keeps its old model value on invalid input, not replaces it with 1. Thus `cells:[{"text":"x","tone":"bogus"}]` has no common add/update outcome, and a width of 0 has no common pane/op outcome. The existing `_norm_cells` is permissive (`store.py:383-398`) and the current pane mutates table fields directly (`vendor/board_editor.js:1666-1700`), so there is no inherited shared policy. Fix: distinguish lenient document-reading fallback from strict writer validation; pin field-by-field add/update/pane behavior (including wrong list types, unknown tone/align and nonpositive widths), and require equivalent accepted writes to produce the same normalized document.

8. MAJOR — Y4.5/Y6 — new-actionable — The table-level align fallback has no complete writer contract. Y4.5 reads `table.align` after cell align (`docs/SPEC-v1.5-panel.md:125-129`), and Y1.5 says this makes table alignment a visible control (`:156-158`). But `add_table`'s promised signature/payload omits align (`:193-202`), Y2 reserves `right` for a cell (`:74`), and the checked-in table update returns before ordinary align writing (`store.py:776-783,801-806`); `_norm_align` only writes left/center (`:260-262`). Fix: specify whether the table default may be right, include or explicitly exclude align in `add_table`, and require `update_node` to validate and write/clear table align with the same values as the pane; test a table with no own cell align under each supported table default.

9. MAJOR — Y0/Y4.7 — new-actionable — No lane owns the JS note renderer that Y4.7 must change. Y4.7 promises both note paths will use text size/bold (`docs/SPEC-v1.5-panel.md:149-152`). Y0 allocates T only `tableSvg` and its callees in JS, P only the panel, and leaves other rendering regions untouched (`:17-29`). The separate `noteSvg` for notes-list entries still emits constant `FONT` with no bold handling (`vendor/board_editor.js:592-611`); it is not called by `tableSvg`. Fix: assign JS `noteSvg` (and its mirror `vendor/boardkit.py:1108-1124`) explicitly to T or the orchestrator, and assign notes-list panel writes to P; gate both note representations with absent, small/large and bold fields.

10. MAJOR — Y8/Y4.4 — new-actionable — The v1.5 overlay check rejects the required base rectangle. Y4.4 requires a base rect followed by four differently toned cell rects on fixture `t2` (`docs/SPEC-v1.5-panel.md:119-123`; `docs/fixture-v1.5.json:16-45`). `tests/test_editor.py:513-515` captures **every** tone-filled rect, including the base `default` rect, but compares it to only `[accent, muted, muted, warn]`. The scratch-copy probe applied that exact regex to a correct base+four-overlay fragment and returned `[default, accent, muted, muted, warn]`. Fix: identify the base rect separately and compare only subsequent cell overlays (preferably by coordinates), asserting base tone, four overlay boxes and draw order.

11. MAJOR — Y8/Y4.6 — new-actionable — Required pre-existing checks contradict the geometry already checked in. The v1.4 fixture renderer produces two horizontal dividers and one vertical, three paths total (scratch-copy render of `docs/fixture-v1.4.json`); `tests/test_render.py:376-383` also expects three. But `tests/test_editor.py:420-421` demands four, so the editor gate fails before a correct v1.5 implementation is considered. Its existing `resize` self-test still requires an auto 3×2 header table height of 100 (`vendor/board_editor.js:2466-2489`) despite the checked-in `nodeSize` resolving 76 (`:370-377`) and Y8 requiring old steps to pass (`docs/SPEC-v1.5-panel.md:263-267`). Fix: have the orchestrator correct the stale path count and the height/handle expectation to 3 and 76 before treating the gate as an implementation verdict; add a guard that both assertions exercise the actual table.

12. MAJOR — Y2/Y8 — new-actionable — Replacing the selects necessarily fails the orchestrator-owned old surface assertions. Y2 forbids a `<select id="ck-kind">` and `<select id="ck-end">` (`docs/SPEC-v1.5-panel.md:66-78`), but `tests/test_editor.py:397-404` still parses exactly those select tags and demands all `KINDS`/`HEADS` as option values; it does not inspect the new buttons. `tests/test_render.py:332-336` likewise requires `<option>` entries under the old picker. Fix: update the orchestrator-owned editor assertions and T-owned render assertions to count the actual button groups, names/pressed states and marker glyphs; keep no select-only assertion for a replaced control.

13. MINOR — Y4.1/Y8 — new-actionable — The named empty-object test is vacuous. `tests/test_editor.py:522-523` only checks that no empty `<text></text>` occurs in `t2`, but its sole object cell has nonempty `"38%"` (`docs/fixture-v1.5.json:41-45`); the empty entry at `:40` is a plain string. A renderer that stringifies `{text:""}` incorrectly still passes this assertion. The tone-precedence assertion at `tests/test_editor.py:516-517` also checks only a multiset, not which cell has which tone. Fix: add an object cell with `text:""` to a dedicated probe, assert that it creates no text, and locate each overlay by its row/column geometry to falsify swapped precedence.

14. MINOR — Y5/Y3 — new-actionable — The specified column-width input rejects its own default under native number-step validity. `docs/SPEC-v1.5-panel.md:171-173` requires `min="0.1"`, `step="0.5"`, and default width 1. With HTML step validation anchored at `min`, valid values are 0.1, 0.6, 1.1, …; 1 is a step mismatch, yet the pane is told not to write invalid values (`:92-95`). Fix: use `step="any"` for all positive decimal widths or choose a min/step pair that admits 1, and test default 1 as well as fractional positive and nonpositive entries.
