# SPEC v1.3 canvas — independent gap pass (project round 2; v1.3 round 1)

Confirmed against the checked-in tree: the v1.2 renderer currently emits a default arrow marker with `refX="10"` (reproduced from a scratch copy of `vendor/`), and its unmodified edge uses the plain `ck-head-default-arrow` id. The v1.3 fixture exists; `tests/test_editor.py:331-351` already includes a v1.3 parity comparison and checks the new self-test names, and `.github/workflows/tests.yml` invokes that suite. These are checks of the baseline and gate wiring, **not** claims that the in-flight v1.3 implementations pass.

Standard: this repository has no `AGENTS.md` invariant block or `SECURITY.md`. I used the supplied fallback: a worker with this repository and no other context must be able to implement the spec, and the spec must be internally consistent. The checked-in v1.2 implementation and tests are the independent reality checks. I compared against the prior findings in `docs/SPEC-v1.2-primitives.gaps-r1.md`; none below repeats one of those six findings.

1. **MAJOR — new-actionable — The zoom toolbar has no permitted writer.** `docs/SPEC-v1.3-canvas.md:10-16` gives lane I only `vendor/board_editor.js` and lane E `vendor/boardkit.py`; `:20-24` nevertheless gives I the toolbar buttons it adds, while W1.5 (`:72-76`) requires three actual HTML buttons and a readout. Today's toolbar is constructed in `vendor/boardkit.py:984-997`, not in the editor script. If I honors its file boundary, its zoom handlers have no controls; if it edits the page factory, it violates the frozen lane map and conflicts with E's file. **Fix:** assign W1.5's `boardkit.page()` HTML explicitly to lane E or the orchestrator (with the exact ids/actions and integration handoff), and assign the JS handlers/readout to I. Gate the presence and operation of the controls in the generated page.

2. **MAJOR — new-actionable — The edge panel cannot show the new fields under the stated edit split.** W3.4 (`docs/SPEC-v1.3-canvas.md:145-152`) requires `openPanel()` to populate the effective side and size values, but W0 (`:18-24`) limits E's panel work inside `board_editor.js` to handlers added after `bind("ck-end", …)`; `openPanel()` is earlier at `vendor/board_editor.js:605-640`. I's ownership list covers selection but does not assign these edge-control population changes. A lane following W0 literally can add selects and change handlers but will leave their displayed values at the HTML defaults on selecting an edge, allowing an unrelated edit to overwrite an explicit value. **Fix:** explicitly give E the three `openPanel()` reads/disabled-state changes (or make I own them with a named handoff); specify a test that selects an edge with nondefaults, then a node, then the edge again and checks values and enabled states.

3. **MAJOR — new-actionable — The default marker geometry contradicts the back-compat requirement.** W3.3 (`docs/SPEC-v1.3-canvas.md:136-143`) requires `refX`/`refY = box / 2`, so a medium marker has `refX="5"`; the same section requires an existing document to render byte-identically. On a scratch copy, `boardkit.render_svg()` of an ordinary two-node, one-edge board emits `<marker id="ck-head-default-arrow" viewBox="0 0 10 10" refX="10" refY="5" markerWidth="11" markerHeight="11" ...>` and the edge refers to that id (`vendor/boardkit.py:586-597,645-672`). The changed `refX` breaks byte identity and moves the arrow tip from its endpoint; `viewBox="0 0 10 10"` also means `box/2` is not a general way to keep the marker's tip anchored as its display size varies. **Fix:** retain `refX="10"`, `refY="5"` for medium and specify reference coordinates in marker-viewBox units for other sizes (or deliberately change geometry and withdraw the byte-identical/back-compat promise). Test the actual default marker attributes and the rendered tip alignment, not only its id.

4. **MAJOR — new-actionable — The claimed existing pointer math is wrong after pan or pointer-anchored zoom.** W1.2 (`docs/SPEC-v1.3-canvas.md:57-60`) changes the `viewBox` origin to `view.x,view.y` but says the existing conversion keeps working; W1.3 (`:62-66`) requires the document point under the cursor to remain fixed. Today's `toSvgPoint()` at `vendor/board_editor.js:480-487` returns `(clientX - rect.left)/scale` and the analogous Y, without adding either viewBox origin. For `viewBox="100 50 450 230"`, a pointer on the SVG's upper-left maps to `(0,0)` in that code but is actually `(100,50)`. Dragging after a pan, marquee bounds and cursor-anchored zoom will jump or select the wrong region. **Fix:** explicitly require adding `parseFloat(vb[0])` and `parseFloat(vb[1])` in the pointer transform (or use the SVG screen CTM inverse); test the conversion and drag/marquee/zoom anchoring at a nonzero view origin.

5. **MAJOR — new-actionable — Marquee groups cannot be represented or interacted with.** W2.2 (`docs/SPEC-v1.3-canvas.md:88-93`) says intersecting **groups** are selected, but W2.1 (`:80-86`) restricts selection entries to `node|note|edge`. In the current editor, groups are separate from nodes (`vendor/board_editor.js:404-412,423-427`), and pointerdown only targets `.ck-node, .ck-note` or `.ck-edge` (`:489-516`); there is no group ring or move path. A worker can either silently omit groups from marquee, or insert an unsupported `group` selection that has no panel, drag or delete semantics. **Fix:** either exclude groups explicitly from the W2.2 selection contract, or add `group` to the selection type and define its ring, primary-panel, drag and Delete semantics, with a fixture/self-test covering group intersection.

6. **MAJOR — new-actionable — Plain-click selection and group-drag initiation require different timing.** W2.1 (`docs/SPEC-v1.3-canvas.md:80-85`) says a plain click selects one item; W2.3 (`:95-97`) says dragging *any selected item* moves the whole selection. Today's pointerdown immediately replaces selection with the clicked item and starts the drag (`vendor/board_editor.js:489-507`). If I retains that behavior, selecting two nodes and dragging one collapses selection to one before movement, so the promised group move never happens; merely adding an array does not solve this. **Fix:** specify that pointerdown on an already-selected movable item preserves the selection through drag, while a completed click without drag collapses it to the one item; define a movement threshold and test multi-select → drag one → both move, versus multi-select → click one → only one remains. Clarify that an edge-only selection is not directly draggable unless edge translation is actually intended, since edges currently have no independent position.
